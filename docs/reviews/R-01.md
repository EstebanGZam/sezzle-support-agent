# R-01 — Independent review (T-12)

## Verdict

No BLOCKER was found, but five MAJOR findings should be resolved or explicitly accepted before the first real evaluation run. The central ADR-1 boundary is genuine: substantive production answers come from `LLMResponse.final_json`; the tripwire emits only a signal; the only fixed shopper-facing failure text is `SAFE_FAILURE_ANSWER`. The fake provider's `[fake] offline answer` is an explicit test/CLI stub, not a production policy answer.

The authorization path is structurally strong. `user_id` is captured from the harness in a closure, absent from the tool schema, and never selected by the model. `OrdersRepository.orders_for(user_id)` runs before order/merchant matching; foreign, nonexistent, malformed, and unknown-user misses return the same payload. The registry contains only `get_my_orders`; model-supplied `user_id`, unknown tools, extra calls, and calls after the first round are rejected without execution. Fraud mode withholds the tool. Route derivation also matches architecture §6, including `forced_reason` precedence and the `policy_applied` split between `tool` and `both`.

Loop accounting is otherwise correct: at most one tool execution, at most three semantic calls, `none` mode for post-tool and repair, bounded transport attempts, a shared batch budget, and auth/billing exit 3 after all lines are written. Key provenance is explicit (`GOOGLE_API_KEY` only), `GEMINI_API_KEY` is ignored, SDK retries are disabled, and traces/configs contain only the specified credential fingerprint. I found no visible/adversarial question, ID, or case-specific routing constant in `src/` or the prompt; the golden ID map in `evals/score.py` is expressly required by evaluation §1.

## Findings

### 1. MAJOR — Fraud-mode merchant read-back is allowed when the shopper typed the merchant

**Location:** `src/support_agent/guards.py:556-559,758-763`

**Concrete behavior:** for caller `u002`, the question `I didn't authorize this order from Nordic Kicks` activates fraud mode. The answer `Your Nordic Kicks order is being escalated to a support specialist` passes the merchant check because `_fraud_merchants` excludes merchant names already present in the shopper message. The tool is correctly withheld, but SEC-11 says the fraud answer contains no merchants, and `evals/score.py:346-362` would label the same answer `FRAUD_READBACK` without that exemption.

**Suggested fix:** in fraud mode reject every caller merchant appearing in the answer, regardless of whether the shopper typed it. Add a validator/loop regression test where the fraud question itself names a real caller merchant.

### 2. MAJOR — The not-found order-ID exception does not require a not-found statement

**Location:** `src/support_agent/guards.py:562-574`

**Concrete behavior:** caller `u001` asks about foreign `ord_3006`; the scoped tool returns `not_found`. An answer such as `ord_3006 exists on another shopper's account` receives only an `order_id` warning, so validation succeeds. The code checks only that the ID was typed and the tool payload is `not_found`; it does not check the security §4 requirement that the ID be echoed *in a not-found statement*. This defeats the intended existence-oracle guard if the model asserts existence.

**Suggested fix:** restrict the exception to a narrow positive not-found construction around the echoed ID (for example, “couldn't find ... on your account”); otherwise fail. Add negative fixtures for “exists elsewhere,” “is active,” and “belongs to another account.”

### 3. MAJOR — `escalation_coherence` is defeated by negation

**Location:** `src/support_agent/guards.py:486,642-648`

**Concrete behavior:** with `escalation_reason="fraud"`, the answer `No human or specialist is needed; I will not escalate this` passes because the validator merely searches for any of `human|specialist|agent|team|escalat`. It contains no hand-off and directly contradicts the structured escalation. `tests/test_validator.py:272-283` tests absence versus a positive hand-off, but no negation trap.

**Suggested fix:** require an affirmative hand-off construction such as “connect/pass/escalate/refer ... to [team/agent/specialist]” or “a specialist will review/help,” and add explicit negative tests for “no specialist,” “do not escalate,” and “an agent is not needed.”

### 4. MAJOR — The production agent never supplies the deadline that controls timeout retries

**Location:** `src/support_agent/agent.py:331-349`; `src/support_agent/llm/base.py:341-388`

**Concrete behavior:** `AttemptRunner` retries a timeout only when its `deadline` permits, but `_CaseRun._call` constructs `LLMRequest` without a deadline. In real `answer_case` execution, `deadline` is always `None`, so every retry-eligible timeout gets another full `LLM_TIMEOUT_S` attempt. A tool + invalid answer + repair path can therefore consume up to six 8-second transport attempts, plus backoff, despite the documented case-deadline condition. Gemini deadline tests call the client directly and do not exercise this integration.

**Suggested fix:** establish one absolute per-case deadline in `_CaseRun` and pass it on every `LLMRequest` (or explicitly specify a different bounded policy). Add an `answer_case` test with a fake clock proving later retries/calls stop when the shared deadline is exhausted.

### 5. MAJOR — The scorer omits failure labels that the evaluation spec says are automatic

**Location:** `evals/score.py:386-429`; `tests/test_score.py:27-84`

**Concrete behavior:** a policy case whose `must_include` is `48 hours` and whose answer is `Try again later` fails regex but receives `automatic_labels=[]` and `primary_label=None`. `_automatic_labels` implements only authorization, fraud, unsafe promise, and route labels. It never assigns `INJECTION_FOLLOWED`, `HALLUCINATION`, `OUT_OF_SCOPE_ANSWERED`, or `GROUNDING_MISS`, although evaluation §4 defines automatic or automatic-candidate behavior. The hand-made matrix test has no fixture for these labels, so the acceptance gap remains green.

**Suggested fix:** implement the defined automatic candidates, at minimum `GROUNDING_MISS` for an unmet required fact with no higher-priority contradiction and `OUT_OF_SCOPE_ANSWERED` using the specified category/length rule. Add one known-result fixture per taxonomy branch. If Tier 3 is intentionally cut, say so explicitly in the required unfinished-work documentation instead of presenting the taxonomy as implemented.

### 6. MINOR — The action-claim regex rejects harmless uses of action verbs

**Location:** `src/support_agent/guards.py:443-459,616-625`

**Concrete behavior:** `I opened the policy page to explain the dispute timeline` fails `action_claim` because `_FIRST_PERSON_ACTION_RE` matches `I opened` without requiring an account object. That is a demonstrable false positive against security §4's purpose: blocking claims that the assistant performed a shopper-account action. Repeated repair failure would turn an otherwise safe answer into SEC-10.

**Suggested fix:** couple ambiguous verbs such as `opened`, `moved`, and `removed` to account nouns (dispute, payment, fee, due date, order, limit), while preserving the current direct checks for unambiguous forbidden claims. Add this harmless sentence as a must-pass regression.
