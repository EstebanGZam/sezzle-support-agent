# R-02 — Independent review of the GroqCloud provider

## Verdict

No credential leak or direct tool-authorization regression was found, but three MAJOR findings should be resolved before a real 35–50-case Groq run. Provider keys are isolated correctly (`groq` reads only `GROQ_API_KEY`; `gemini` only `GOOGLE_API_KEY`), the HTTP client does not inherit proxy/netrc state, error text is scrubbed before reaching traces, and config records only the active credential fingerprint. Request construction also preserves the important structural controls: `none` mode exposes only forced `submit_answer`, `parallel_tool_calls` is false, unknown tools remain unexecuted, and `user_id` stays closure-bound outside model arguments. The optional fields added to `AttemptRecord` do not alter the Gemini transport path, and the existing Gemini tests remain green.

## Findings

### 1. MAJOR — Default pacing can turn most of a batch into unsent safe failures

**Location:** `src/support_agent/config.py:43-58,240-245`; `src/support_agent/llm/groq.py:348-368`

**Concrete behavior:** the Groq defaults enable an 8,000-token rolling 60-second window but retain a 30-second case deadline. With a realistic long static prefix, a synthetic sequence of successful 5,500-token calls produced: call 1 on 120b, call 2 on 20b after the primary pacing check refused to wait, then call 3 failed `rate_limit_minute` after three client-side pacing attempts without sending any HTTP request. Because refused waits advance time only through the runner's sub-second retry backoff, a sequential 35–50-case run can consume many remaining cases as immediate safe failures before either model window expires. `tests/test_groq.py:916-926` covers only the first fallback, while `tests/test_config.py:370-374` treats the unsafe default as a warning rather than exercising the next call when both buckets are occupied.

**Suggested fix:** when `LLM_PROVIDER=groq` and pacing is enabled, default `CASE_DEADLINE_S` to the specified 150–180 seconds, or reject configurations whose deadline cannot accommodate a full pacing window plus an attempt. Add a three-call batch regression test that fills both model windows and proves the third call waits and is sent rather than failing unsent.

### 2. MAJOR — A permanently oversized 413 is misclassified from the local estimate

**Location:** `src/support_agent/llm/groq.py:634-678`; `tests/test_groq.py:203-206,734-803`

**Concrete behavior:** the test/provider message says `Limit 8000, Requested 8350`, yet `classify_response(..., est_tokens=2000, tpm_budget=8000)` returns `rate_limit_minute`. Waiting cannot make that 8,350-token request fit; the code then blocks for a minute, fails over, and may retry the same permanently invalid request. This contradicts A-030 requirement 5, which maps 413 to `bad_request`, and the test asserts the implementation's local estimate instead of the provider's concrete limit/request values.

**Suggested fix:** conservatively restore 413 to `bad_request`, or parse trustworthy `Limit`/`Requested` values and classify as minute saturation only when the provider says the individual request fits. Add a behavioral test proving `Requested > Limit` never retries or fails over regardless of the client estimate.

### 3. MAJOR — `tool_use_failed` bypasses the specified repair path

**Location:** `src/support_agent/llm/groq.py:221-224,571-590`; `tests/test_groq.py:362-386,1063-1098`

**Concrete behavior:** a Groq 400 `tool_use_failed` whose `failed_generation` contains schema-valid answer JSON is converted directly into `final_json` and recorded as a successful recovered transport attempt. The model did not call the required `submit_answer` tool and Groq rejected the turn, but the adapter accepts it without the repair semantic call. Architecture §8.1 says `400 tool_use_failed -> repair path`, and A-030 says invalid/non-tool output is malformed and repaired. The new tests encode the undocumented behavior rather than the source-of-truth contract.

**Suggested fix:** return a malformed `AttemptOutput` for every `tool_use_failed` so the existing agent repair path runs. If recovery is an intentional owner decision, approve and update the architecture/task first, then retain tests that also prove normal validation and trace semantics.

### 4. MINOR — Inactive-provider knobs can break Gemini, fake, or Groq startup

**Location:** `src/support_agent/config.py:208-224`

**Concrete behavior:** all provider-specific settings are parsed unconditionally. `LLM_PROVIDER=gemini` with a valid Google key and stale `GROQ_TPM_BUDGET=not-a-number` raises `ConfigError`; `LLM_PROVIDER=groq` is likewise blocked by an invalid `GEMINI_THINKING_LEVEL`; fake mode can be blocked by malformed Groq pacing values. This is a configuration regression despite the requirement that provider settings be isolated and the Gemini path remain unchanged.

**Suggested fix:** read and validate Gemini-only knobs only for Gemini, and Groq-only knobs only for Groq; assign inert defaults for inactive providers. Add cross-provider tests with deliberately invalid inactive settings.
