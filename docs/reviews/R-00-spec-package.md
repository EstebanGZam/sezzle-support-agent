# R-00 — Independent SDD Preparation Package Review

Scope: read-only review of the requested package, without the holdout. Official-file integrity passes `sha256sum -c assessment/SHA256SUMS` (16/16). Verdict: **not ready to implement**. The direction is strong, but the items below should be resolved first.

## Findings

1. **BLOCKER — unresolved model configuration makes IP-01 non-executable.** `specs/architecture.md:§8` leaves `GEMINI_PRIMARY_MODEL` as “owner decision after smoke test”; `.env.example` does the same, while `specs/requirements.md:OWN-06` describes a selected primary and `docs/readiness-checklist.md:§D.1` still requests the decision. IP-01 requires defaults to match architecture, so the implementer must guess whether the model is required, defaulted, or empty. **Fix:** make primary-model selection a blocking owner decision, record it as an OD, and put the same explicit model/fallback semantics in architecture, `.env.example`, ADR-3, and config tests.

2. **MAJOR — detailed agent recommendations are presented as owner-approved architecture.** `docs/decision-log.md:AR-01..AR-04` correctly labels the one-round loop, citation-derived route, validator design, and neutral-facts boundary as agent recommendations “owner may override”; however, `specs/architecture.md:introduction` calls the direction owner-approved and makes all four binding. This blurs the provenance required by P-004. **Fix:** either obtain and log explicit owner approval for those ARs, or label them proposed implementation details pending the implementation-start decision.

3. **MAJOR — several SEZ requirements are actually inferred engineering choices.** `specs/requirements.md:SEZ-C02` adds malformed-line/blank-line behavior absent from the official contract; SEZ-C05 invents per-case continuation; SEZ-N01 requires measured tokens and latency although the brief only requires an ADR explaining trade-offs. In addition, `SEC-01` incorrectly cites “SEZ-F06 hostile input”; F06 is the frozen-date rule. **Fix:** retain the official core under SEZ, move extra robustness and measurement requirements to OWN/SEC, and correct SEC-01’s source to the Eng II hostile-order requirement plus OWN-05.

4. **MAJOR — traceability is incomplete despite the readiness claim.** `specs/tasks.md` has no explicit task mapping for SEZ-F04/F05; the blanket note covers SEZ-P*, not those functional requirements. Conversely every task has at least one requirement, but several verification references are only “eval categories,” with no named T-13/T-14 link. `docs/readiness-checklist.md:§A` therefore overstates complete traceability. **Fix:** add F04/F05 to T-06, T-10, T-13/T-14 as appropriate, and add a generated/manual requirement-to-task-to-test matrix covering every SEZ ID.

5. **MAJOR — route derivation is too fragile for exact route grading.** `specs/architecture.md:§6` turns any executed tool answer into `both` whenever the model emits a policy citation. A harmless POL-01 citation on golden v01 changes the required `tool` route to `both`; the spec acknowledges this but defers it to iteration. The synthetic smoke results already varied between `tool` and `both` for the same task, so this is observed, not hypothetical. **Fix:** resolve the semantic contract before coding—e.g. have the model return a constrained `policy_applied` signal distinct from citations, validate it against tool use, and unit-test all four routes. Do not call this risk merely a future prompt tweak.

6. **MAJOR — the validator will reject safe answers and miss unsafe ones.** `specs/security.md:§4.3` rejects every non-caller `ord_` token, so “I cannot find ord_9999 on your account” is invalid even though adv-d02 expects that safe behavior. Section 4.4 allows all corpus numbers, letting an invented shopper-specific $5/$10 claim through, while correct derived dates/amounts can fail. Sections 4.5–4.6 miss “we moved it,” “your payment is now rescheduled,” and similar voices, yet can reject truthful dispute wording such as “has been paused.” **Fix:** validate typed claims rather than a global number/string union; treat an echoed unverified ID in a not-found statement as a warning; expand action tests with positive and negated contexts; add these exact false-positive/negative fixtures.

7. **MAJOR — hostile-input controls are not as structural as claimed.** `specs/security.md:§3` structurally forces escalation only for fraud/hardship. Fee-waiver demands, exact-limit demands, decline overrides, credit corrections, and dispute actions rely on the model setting `escalation_reason`; the validator checks promises, not under-escalation. Yet ADR-1 says dangerous failures are “impossible or caught.” **Fix:** narrow the claim, and add one-way, non-answering escalation signals or postconditions for explicit human-only action requests, while leaving policy interpretation and response text to the LLM. This stays within P-004’s deterministic-boundary clarification.

8. **MAJOR — execution and trace contracts contradict each other.** `specs/architecture.md:§7` says auth/billing “aborts” the batch, whereas `specs/evaluation.md:§7` requires output lines for all remaining cases via a circuit breaker. IP-04 says fallback is only for “retryable” errors, but architecture sends daily quota exhaustion to fallback while calling it non-retryable. Architecture defines `PROMPT_VERSION` as a hash of the static prefix; evaluation §6 hashes prompt plus tool schema. The trace example uses citations `['02','10']`, `escalation_reason: null`, and `route_declared`, while the final schema uses `POL-02`, the string `none`, and no model-declared route. Architecture §5 also points to nonexistent `security.md §8` instead of §4. **Fix:** publish one canonical state/error/trace schema, define attempt versus semantic-call limits, and correct the cross-reference.

9. **MAJOR — holdout metadata is already leaked.** `specs/evaluation.md:§3` publishes holdout IDs and category assignments (`h01`…`h15`), despite §1 calling the holdout unseen until the final run. An implementer can tune specifically for its category distribution without reading the file. **Fix:** remove all holdout IDs and category mappings from the repository; keep only aggregate, precommitted evaluation criteria outside the implementation checkout.

10. **MAJOR — several development regexes are weak or unfair.** I checked adv-d01, d04, d07, d09, d11, d14, d15, d16, d18, d21, d22, and d25 against policies/orders; their underlying order facts and routes are generally defensible. Problems: d05 has no `must_include`, so an empty answer with route `tool` passes; d06’s “your limit is” rejects a correct negation; d07 can repeat the injected 60-day rule while also mentioning two weeks; d14’s `3.10` uses wildcard dots; d15 can pass with generic refund policy without resolving the specific refund; d18 forbids “waived” even in a safe denial; d25 omits the required overdue-balance/fees steps and the $10 fee. **Fix:** strengthen positive assertions, use literal/range separators, avoid negation traps in dev cases, and reserve known-bad official golden regexes for diagnostic `weak_check` reporting only.

11. **MAJOR — the implementation prompts still require guessing.** `docs/implementation-prompts.md:IP-01` creates `llm/` placeholders outside T-01/T-02’s sole-owned files. IP-06 runs the full golden set with `LLM_PROVIDER=fake` but never defines the script/default responses that make that CLI command executable. The common verification omits `ruff format --check`, contrary to AGENTS.md. **Fix:** align file ownership, define a fixture/script input for fake CLI execution, and use the repository-wide lint/format/test command at each integration gate.

12. **MAJOR — the plan is not credible within ~2 hours.** Eighteen tasks include a provider abstraction, retry/fallback/circuit breakers, a multi-check repair validator, extensive trace analytics, CI, packaging, 25 dev cases, a noise-floor rerun, baseline/final/holdout runs, and documentation. This risks missing the highest-weight deliverables. **Fix/cut order:** first cut CI and zip automation; then fallback/circuit-breaker sophistication; then automated failure taxonomy and noise-floor analytics; then derived-fact breadth and local holdout machinery. Preserve the working LLM, CLI, caller-scoped read-only tool, no-write boundary, minimal schema/safety validation, visible first/final runs with one measured iteration, exactly three ADRs, PROMPTS.md, and README.

13. **MINOR — ADR format and measurement wording need cleanup.** `DECISIONS.md` has exactly three records and each is under roughly ten lines, but ADR-3 lacks an explicit **Why** field required by both the brief and T-15. Its “median 2.0–3.0 s” compresses measured medians of 2.67 s and 3.04 s and hides the tiny synthetic n=3 caveat; ADR-1’s “impossible or caught” is not supported by the validator design. **Fix:** add a labelled Why line, quote exact measurements with sample/caveat, replace absolutes, and retain placeholders until real assessment runs exist.

## Top 7 fixes before implementation

1. Obtain and propagate the primary/fallback model owner decision.
2. Resolve provenance: approve or clearly mark AR-01..AR-04 as proposed.
3. Correct SEZ/OWN/SEC classification and complete the traceability matrix.
4. Replace citation-based routing with a stable, tested route signal.
5. Redesign validator checks around typed/contextual claims and under-escalation.
6. Canonicalize error, retry, trace, prompt-version, and fake-LLM contracts.
7. Remove holdout metadata leakage, repair dev regexes, and reduce scope to the two-hour MVP.
